# Q: Users are getting 502 / 504 / 413 / 403 / 404 errors from Nginx. How do you troubleshoot each one?

> **Level:** Advanced · **Asked in:** DevOps, SRE, Support Engineer, Platform Engineer

## 🎯 Short answer (say this in the interview)

I start with the same checklist every time: `nginx -t` to validate config, `nginx -T` to see the real merged config, `systemctl status nginx`, and most importantly `/var/log/nginx/error.log`, because the error log tells you *why*. Then I narrow down by status code: **502** means Nginx could not get a valid response from the backend (down, wrong port, socket permissions, crash), **504** means the backend was too slow (timeouts), **413** means the request body is larger than `client_max_body_size`, **403** is usually file permissions, a missing index file, or a `deny` rule, and **404** is usually a wrong `root`/`alias` or a missing `try_files` for SPAs. I always `curl` the backend directly from the Nginx box to separate "Nginx problem" from "app problem".

## 🧩 Scenario

It's Monday morning. The monitoring dashboard shows a spike of 5xx errors. Support tickets say: "site shows 502", "file upload fails with 413", "refreshing the React page gives 404", and "the new docs folder says 403 Forbidden". You are on call. You need a calm, repeatable method that gets each issue fixed quickly.

## 💼 Use case

- On-call incident response for any website or API behind Nginx.
- Post-deployment checks (new backend port, new upload feature, new SPA route).
- Interview "scenario" rounds — this is one of the most common practical questions.

## ⚙️ How it works

```text
            client
              │  request
              ▼
     ┌──────────────────┐   bad config / port busy  → Nginx won't start ("address already in use")
     │      NGINX       │   body too big            → 413 (client_max_body_size)
     │                  │   deny rule / perms       → 403
     │  location match  │   file not found          → 404
     └────────┬─────────┘   client gave up          → 499 (only in access log)
              │ proxy_pass
              ▼
     ┌──────────────────┐   not running / wrong port / refused / crashed  → 502
     │     BACKEND      │   SELinux blocks the connection (RHEL)          → 502
     │  (Node/PHP/...)  │   too slow (> proxy_read_timeout)              → 504
     └──────────────────┘
```

**General debugging checklist (run in this order)**

```bash
sudo nginx -t                                   # 1. is the config valid?
sudo nginx -T | less                            # 2. what config is REALLY loaded (all includes merged)?
systemctl status nginx --no-pager               # 3. is nginx running? recent errors?
sudo tail -n 50 /var/log/nginx/error.log        # 4. the WHY — always read this
sudo tail -n 50 /var/log/nginx/access.log       # 5. status codes, paths, timings
sudo ss -tlnp                                   # 6. what is listening on which port?
curl -v http://127.0.0.1:3000/                  # 7. hit the backend DIRECTLY (skip nginx)
curl -v -H "Host: app.example.com" http://127.0.0.1/   # 8. hit nginx locally with the right Host
namei -l /var/www/app/index.html                # 9. permissions on every folder in the path
journalctl -u nginx --since "10 min ago"        # 10. startup errors from systemd
```

Tip: to see more details for one problem, temporarily raise the log level in `/etc/nginx/nginx.conf`: `error_log /var/log/nginx/error.log info;` (remember to set it back).

## 🛠️ Practical: step by step

### 1. 502 Bad Gateway

**Symptom:** Browser shows `502 Bad Gateway`. Nginx is up, the backend is not answering correctly.

**Typical error.log lines:**

```text
connect() failed (111: Connection refused) while connecting to upstream, client: 203.0.113.5, server: app.example.com, request: "GET / HTTP/1.1", upstream: "http://127.0.0.1:3000/", host: "app.example.com"

connect() to unix:/run/php/php8.1-fpm.sock failed (2: No such file or directory) while connecting to upstream

connect() to unix:/run/php/php8.1-fpm.sock failed (13: Permission denied) while connecting to upstream

upstream prematurely closed connection while reading response header from upstream

upstream sent too big header while reading response header from upstream
```

**Root causes and fixes:**

```bash
# a) Backend is not running / wrong port
sudo ss -tlnp | grep -E ':3000|php'       # is anything listening?
curl -v http://127.0.0.1:3000/            # does the backend answer directly?
sudo systemctl restart myapp              # or: pm2 restart all / docker start api

# b) App listens only on another interface (e.g. 127.0.0.1 vs container IP) → fix the app's bind address
#    or fix proxy_pass to the address it actually listens on.

# c) PHP-FPM socket path is wrong (version mismatch, e.g. 8.1 vs 8.3)
ls -l /run/php/                            # real socket name
```

```nginx
# /etc/nginx/sites-available/app.conf — fix the socket path to match `ls /run/php/`
location ~ \.php$ {
    include snippets/fastcgi-php.conf;
    fastcgi_pass unix:/run/php/php8.3-fpm.sock;
}
```

```nginx
# "upstream sent too big header" (large cookies / JWT headers) — in the proxied location:
proxy_buffer_size 16k;
proxy_buffers 8 16k;
proxy_busy_buffers_size 32k;
```

```bash
# d) "prematurely closed connection" → the app crashed or closed the socket; check app logs
journalctl -u myapp -n 100 --no-pager
```

### 2. 504 Gateway Timeout

**Symptom:** Request hangs and then `504 Gateway Time-out`, often exactly after 60 seconds.

**Typical error.log line:**

```text
upstream timed out (110: Connection timed out) while reading response header from upstream, client: 203.0.113.5, server: app.example.com, request: "GET /reports/annual HTTP/1.1", upstream: "http://127.0.0.1:3000/reports/annual"
```

**Root causes:** slow DB query or report, backend overloaded, backend unreachable (firewall dropping packets), timeout too low for a legitimately long operation.

**Fix:** first make the backend faster or move long jobs to a background queue. If the operation really is long, raise timeouts **only for that path**:

```nginx
# /etc/nginx/sites-available/app.conf
location /reports/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_connect_timeout 10s;   # time to establish TCP connection (cannot exceed ~75s)
    proxy_send_timeout    120s;  # between two writes to the backend
    proxy_read_timeout    300s;  # between two reads from the backend (default 60s)
}
```

For PHP-FPM the equivalent is `fastcgi_read_timeout 300s;` (and PHP's own `max_execution_time` / FPM's `request_terminate_timeout`).

```bash
# Time the backend directly to prove where the delay is
curl -o /dev/null -s -w "total: %{time_total}s\n" http://127.0.0.1:3000/reports/annual
```

### 3. 413 Request Entity Too Large

**Symptom:** File upload fails instantly with `413`. Default limit is **1 MB**.

**Typical error.log line:**

```text
client intended to send too large body: 5242880 bytes, client: 203.0.113.5, server: app.example.com, request: "POST /upload HTTP/1.1", host: "app.example.com"
```

**Fix** — valid in `http`, `server` or `location`:

```nginx
# /etc/nginx/sites-available/app.conf
server {
    # ...
    client_max_body_size 2m;            # small default for everything

    location /upload {
        client_max_body_size 50m;       # bigger limit only where needed
        proxy_pass http://127.0.0.1:3000;
        proxy_request_buffering off;    # optional: stream big uploads to the backend
    }
}
```

Also check: the backend's own limit (e.g. Express `body-parser` limit, PHP `upload_max_filesize` / `post_max_size`), and any load balancer or Ingress in front (`nginx.ingress.kubernetes.io/proxy-body-size` in Kubernetes).

### 4. 403 Forbidden

**Typical error.log lines and causes:**

```text
directory index of "/var/www/docs/" is forbidden
```
→ No `index.html` in the folder and `autoindex` is off. Add an index file, fix the `index` directive, or (if intended) `autoindex on;`.

```text
open() "/var/www/docs/index.html" failed (13: Permission denied)
```
→ Worker user `www-data` can't read the file or can't **traverse** (execute) a parent folder.

```text
access forbidden by rule, client: 203.0.113.5
```
→ An `allow`/`deny` rule matched.

**Fix permissions:**

```bash
namei -l /var/www/docs/index.html          # look for a folder without x for "others"/www-data
sudo chown -R www-data:www-data /var/www/docs
sudo find /var/www/docs -type d -exec chmod 755 {} \;
sudo find /var/www/docs -type f -exec chmod 644 {} \;
sudo -u www-data cat /var/www/docs/index.html   # test as the worker user
```

Common trap: serving from `/home/ubuntu/site` — home folders are often `750`, so `www-data` can't enter them. Move the site to `/var/www/`.

### 5. 404 Not Found

**Typical error.log line:**

```text
open() "/var/www/html/images/logo.png" failed (2: No such file or directory)
```

The path in the log is exactly where Nginx looked. Compare it with where the file really is.

**`root` vs `alias` mistake:**

```nginx
# Files are in /var/www/assets/logo.png and the URL is /static/logo.png

location /static/ {
    root /var/www/assets;     # WRONG: looks for /var/www/assets/static/logo.png
}

location /static/ {
    alias /var/www/assets/;   # RIGHT: /static/ is replaced → /var/www/assets/logo.png
}
```

**SPA (React/Vue/Angular) refresh gives 404:** the route `/dashboard` exists only in JavaScript, not on disk. Send unknown paths to `index.html`:

```nginx
# /etc/nginx/sites-available/spa.conf
server {
    listen 80;
    server_name app.example.com;
    root /var/www/spa/dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;   # file → folder → fall back to the SPA
    }
}
```

Also check: `proxy_pass` with/without a trailing slash changes the path sent to the backend (`proxy_pass http://api:3000/;` strips the matched location prefix; without the slash it keeps it).

### 6. 499 Client Closed Request

Nginx-specific code, written only to the **access log**: the client disconnected before Nginx sent a response. It is not an error page users see.

**Causes:** backend too slow and the user/browser/load balancer gave up first; mobile network drops; a health checker with a short timeout.

```bash
# How many 499s and on which URLs? ($status is field 9 in the default "combined" format)
sudo awk '$9 == 499 {print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head
```

**Fix:** treat it like a latency problem — speed up the backend, or check that the timeout of the load balancer in front of Nginx is not shorter than Nginx's `proxy_read_timeout`.

### 7. "Address already in use" when starting Nginx

```text
nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)
```

```bash
sudo ss -tlnp 'sport = :80'                # who owns port 80?
# example: users:(("apache2",pid=812,fd=4))
sudo systemctl stop apache2 && sudo systemctl disable apache2
sudo systemctl start nginx
```

Other causes: an old Nginx started by hand (not via systemd) is still running (`sudo pkill nginx` then `sudo systemctl start nginx`), or two `listen` lines bind the same address in a conflicting way.

### 8. SELinux on RHEL / Rocky / Alma: 502 even though the backend works

```text
connect() to 127.0.0.1:3000 failed (13: Permission denied) while connecting to upstream
```

`curl 127.0.0.1:3000` works from your shell, but Nginx gets "Permission denied". SELinux blocks the `httpd_t` domain (which Nginx runs in) from making network connections by default.

```bash
getenforce                                     # Enforcing?
sudo ausearch -m avc -ts recent | grep nginx   # see the denial
sudo setsebool -P httpd_can_network_connect 1  # allow nginx to connect to backends (-P = permanent)

# For files served from a custom folder (403 with SELinux):
sudo semanage fcontext -a -t httpd_sys_content_t "/srv/site(/.*)?"
sudo restorecon -Rv /srv/site
```

Don't "fix" it with `setenforce 0` in production; that disables SELinux protection for everything.

## 📁 Files involved

| File / Folder | What it does here |
|---|---|
| `/var/log/nginx/error.log` | The reason behind every error — read first |
| `/var/log/nginx/access.log` | Status codes (including 499), paths, frequency |
| `/etc/nginx/nginx.conf` | `error_log` level, global settings |
| `/etc/nginx/sites-available/*.conf` | `proxy_pass`, timeouts, `client_max_body_size`, `root`/`alias`, `try_files` |
| `/run/php/php*-fpm.sock` | PHP-FPM socket that must match `fastcgi_pass` |
| `/var/www/` | Web root — permissions matter for 403 |
| `/var/log/audit/audit.log` | SELinux denials on RHEL-family systems |

## ✅ Verify it works

```bash
sudo nginx -t && sudo systemctl reload nginx

# 502/504 fixed: expect 200 and a sensible time
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://app.example.com/

# 413 fixed: upload a 10 MB test file
head -c 10M /dev/urandom > /tmp/test.bin
curl -s -o /dev/null -w "%{http_code}\n" -F "file=@/tmp/test.bin" http://app.example.com/upload
# expect anything except 413 (e.g. 200 from the app)

# 403 fixed
curl -I http://app.example.com/docs/            # expect HTTP/1.1 200 OK

# SPA 404 fixed: deep link returns index.html
curl -s -o /dev/null -w "%{http_code}\n" http://app.example.com/dashboard/settings   # expect 200

# Watch errors live while you test
sudo tail -f /var/log/nginx/error.log
```

## ⚠️ Common mistakes

- Looking only at the browser error page and never opening `error.log`.
- "Fixing" 504 by setting all timeouts to 3600s globally — this hides slow code and ties up connections.
- Raising `client_max_body_size` in Nginx but forgetting the app's or the Ingress's own limit.
- Using `chmod -R 777` to fix 403. Use correct ownership and `755`/`644`.
- Mixing up `root` and `alias` (and forgetting the trailing `/` on `alias`).
- Restarting Nginx when the actual problem is the backend.
- Disabling SELinux instead of setting the right boolean or file context.

## 🔁 Follow-up questions interviewers ask

1. **502 vs 504 — what's the difference?**
   502: the backend gave an invalid/no response (refused, crashed). 504: the backend didn't answer within the timeout.
2. **Where does 499 come from?**
   It's Nginx's own code for "client closed the connection before the response"; it only appears in the access log.
3. **What does `nginx -T` give you that `nginx -t` doesn't?**
   It prints the full effective config, including all included files, so you can see which `server`/`location` really applies.
4. **How do you tell if a 502 is Nginx's fault or the app's?**
   `curl` the backend directly from the Nginx host. If that fails too, it's the app (or network/SELinux), not Nginx.
5. **Why might you get 404 for `/api/users` when the backend has that route?**
   Usually the `proxy_pass` trailing slash rewrote the path (e.g. sent `/users` instead of `/api/users`), or the request matched a different `location`.
